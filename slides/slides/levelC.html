Level C · We hit a weak verifier — and fixed it

Our first verifier false-positived on the patched version

The trap

The 0.5.0 patch catches RecursionError and re-raises it chained — so the traceback still contains "RecursionError". A naive check passes the fixed code.

Our fix

Check the terminal exception that actually escapes: accept only a bare RecursionError from sqlparse/sql.py, reject if it became SQLParseError.

Vulnerable 0.4.4  ✓ flag

Patched 0.5.0  ✗ rejected (exit 1)

This is exactly the bug the paper's Verifier Critic exists to catch — we met it and fixed it ourselves.

NT521.R11.ANTN · Reproducing CVE-GENIE · CVE-2024-4340, CWE-674

We wrote our own exploit and verifier for the sqlparse DoS. Our first verifier was fooled by the patched version because the fix re-raises the recursion error chained, leaving the string in the traceback. Fixing it by inspecting the terminal exception shows we understand the vulnerability at the mechanism level — and demonstrates why the developer/critic loop matters.
